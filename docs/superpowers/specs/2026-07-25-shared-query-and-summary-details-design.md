# Shared Query and Summary Details Design

## Goal

Make the current server-owned jobs visible consistently across browser windows, show product-library online-query logs in the search result area, and make transfer summaries easy to inspect by product and by failed barcode.

## Scope

- Query page: browser windows signed in as the same tool account display the account's latest background query job, including progress, item states, failures, and logs.
- Product-library page: the existing one-second status polling renders the latest online-query state and logs directly below the search controls.
- Transfer page: the summary card lists product name, code, and quantity. A product row opens its barcode details. A separate failed/excluded entry opens barcode reasons.

## Architecture

The Flask process remains the source of truth. The query status endpoint accepts an explicit `latest=1` discovery mode so a browser with a stale local job ID can adopt the account's current job. The query page continues polling a specific active job, while an idle background sync periodically discovers a newer job started in another browser.

The product-library page keeps its existing background job and polling route. No new transport is required; the page renders the latest log rows into the existing `lookupBox` live region on every poll.

Transfer summaries gain a normalized `failure_details` list generated by the backend. The frontend renders compact product buttons and uses one existing-style modal for product barcode details or failed/excluded barcode reasons.

## Data Contracts

### Background query status

- `GET /api/crm/background-batch/status?latest=1` ignores a stale `job_id` and returns the latest job owned by the current tool account.
- Requests without `latest=1` retain the existing explicit-job behavior.

### Transfer summary failures

Each `failure_details` row contains:

- `barcode`
- `reason`
- `category`: `missing`, `incomplete`, or `excluded`

Direction mismatches remain in `blocked` because they are warnings and do not prevent submission.

## UI Behavior

- Query pages discover shared state at load, every two seconds while idle, on visibility return, and on `pageshow`.
- Product-library live output shows barcode, channel, current state, elapsed time, and recent log lines in the search result area. Completed successful queries still end by showing the matched product.
- Transfer product rows are keyboard-accessible buttons. The detail modal shows product name, model, code, quantity, and all barcodes. The failure entry shows every failed/excluded barcode and its reason.

## Error Handling

- A failed status discovery leaves the currently rendered query state intact and retries later.
- Product-library polling errors show a live error message without discarding existing logs.
- Empty transfer products or failures render an explicit empty state instead of opening a blank modal.

## Testing

- Backend route test proves `latest=1` replaces a stale requested job ID.
- Backend summary test proves failure reasons are normalized after unmatched barcodes are excluded.
- Frontend contract tests cover shared query discovery, inline product-library live output, and transfer detail controls.
- Full unit tests, JavaScript syntax checks, and `git diff --check` run before completion.
