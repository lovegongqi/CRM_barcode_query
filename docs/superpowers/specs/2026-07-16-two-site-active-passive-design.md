# 怡口 CRM 条码查询工具双站高可用设计

## 1. 目标

在不改变桌面版使用方式的前提下，将服务器版部署为香港主站、新加坡备用站：

- 正常情况下，`https://crm.mlmll.cn` 只访问香港站。
- 香港应用或整机故障时，自动切换到新加坡站。
- 香港恢复后，先补齐新加坡故障期间产生的数据并完成校验，再自动切回香港。
- 两站业务数据在正常网络下 5 分钟内同步；允许的最大数据丢失窗口为 5 分钟。
- 用户主动删除的数据不得因另一台服务器恢复或同步而重新出现。
- CRM 浏览器会话和运行中的查询、移库任务不跨服务器迁移。

## 2. 范围与约束

### 2.1 纳入统一存储的数据

- 条码查询结果、详情和压缩后的 CRM 报表 HTML。
- 条码备注、结单状态、归档状态等元数据。
- 条码匹配规则和产品信息。
- 目标分销商、分销商删除记录和使用历史。
- 工具账号、权限、运行配置和加密后的 CRM 记住密码数据。
- 操作日志、查询日志、移库日志、结单日志和同步审计记录。

### 2.2 保持节点独立的数据

- Playwright/Chromium 用户目录和 CRM 登录 Cookie。
- 查询通道、移库通道的当前浏览器进程。
- 正在执行的查询、移库、结单任务及其内存状态。
- 临时下载和可重新生成的导出文件。

因此，两台服务器需要分别登录 CRM。发生切换时，已完成结果不会丢失；切换瞬间正在执行的任务会明确标记为中断，并由用户在备用站重新提交。

### 2.3 不在本期范围内

- 美国服务器和群晖不作为运行、数据库或调度节点。
- 不在两个站点之间共享 Chromium profile。
- 不实现同一个查询任务跨服务器拆分或迁移。
- 不改动 Windows、macOS 桌面版的本地文件存储模式。

## 3. 总体架构

```text
用户
  |
  v
Cloudflare Load Balancer
  |-- 主池：香港 Flask/Gunicorn + 香港 PostgreSQL
  `-- 备池：新加坡 Flask/Gunicorn + 新加坡 PostgreSQL

Cloudflare Worker + Durable Object
  `-- 只保存 active_site、epoch、心跳和切换状态

香港应用 <---- 增量事件同步 ----> 新加坡应用
香港数据库 <---- 快照备份/恢复 ---> 新加坡数据库
```

Cloudflare Load Balancer 负责访问入口和健康检查，Worker + Durable Object 负责唯一活动站租约。二者职责分开：负载均衡器决定流量去哪，租约确保同一时刻只有一个站点接受业务写入，避免网络分区时两边同时修改数据。

Durable Object 不保存条码或账号等业务数据，只保存极少量高可用协调状态。该调用量远低于免费额度。

## 4. 应用存储改造

### 4.1 双存储后端

增加统一的存储接口，业务代码不再直接读写散落的 JSON/HTML 文件：

- 服务器模式：设置 `DATABASE_URL` 后使用 PostgreSQL。
- 桌面模式：未设置 `DATABASE_URL` 时继续使用现有本地文件，保持安装包兼容。

本次只抽取当前业务实际使用的读、写、删除和列表操作，不进行无关的 `app.py` 重构。

### 4.2 PostgreSQL 数据模型

核心表按业务边界拆分：

- `barcode_reports`：条码、结构化查询字段、压缩 HTML、查询时间和来源节点。
- `barcode_metadata`：备注、归档、结单状态、服务单号等可变字段。
- `product_rules`：前缀、产品编码、产品名称和更新时间。
- `distributors`：分销商名称、来源、最近成功使用时间和删除状态。
- `tool_accounts`、`runtime_settings`、`crm_credentials`：账号、权限、配置和加密凭据。
- `operation_logs`：查询、移库、结单和系统操作记录。
- `sync_events`：每次新增、修改和删除的不可变同步事件。
- `sync_cursors`：每个对端已确认的同步位置。

HTML 使用 gzip 压缩后写入 `bytea`，避免大量小文件并保留完整详情页。导出 Excel 和临时文件按需生成，不作为必须同步的数据。

### 4.3 凭据保护

CRM 记住密码使用共享环境变量 `CRM_CREDENTIALS_KEY` 加密后入库；密钥只放在两台服务器的部署环境中，不提交 Git。Flask 会话使用两站相同的 `SECRET_KEY`，站点切换后工具账号登录可继续使用。

## 5. 增量同步与删除语义

### 5.1 写入规则

每次业务写入在同一数据库事务中同时完成：

1. 更新对应业务表。
2. 追加一条带全局 UUID、实体类型、实体键、操作类型、有效负载、站点 epoch 和本地序号的 `sync_events` 记录。

对端按游标拉取事件并幂等应用；同一事件 UUID 重复到达不会重复执行。同步程序每 60 秒运行一次，连续 5 分钟未成功同步即告警，并将备用站标记为“数据滞后”。

只有持有当前活动租约且 epoch 匹配的站点接受用户写入。备用站只接收同步事件、健康检查和管理检查，普通写请求返回只读提示。这样不依赖服务器时钟做冲突覆盖，也不会出现双主写入。

### 5.2 删除不会复活

删除不是直接抹掉记录，而是写入删除事件和墓碑：

- 业务表记录标记 `deleted_at`、`deleted_by`、`delete_event_id`。
- 删除事件和普通更新一样同步到对端。
- 墓碑至少保留 30 天，并记录两站确认状态。
- 两站都确认后，后台可删除大体积 HTML 内容，但保留最小墓碑用于防复活。
- 节点离线超过墓碑保留窗口，重新上线前必须从活动站执行完整快照同步，不允许直接对外服务。

因此，用户主动删除条码、分销商或匹配规则后，旧节点恢复时只能接收删除事件，不能把旧内容重新写回来。

### 5.3 同步安全

两站同步接口使用 HTTPS、固定对端 IP 白名单和 HMAC 签名。签名包含时间戳、请求体摘要和节点标识；过期或重复请求拒绝处理。同步密钥独立于工具账号密码。

## 6. 自动切换状态机

### 6.1 正常状态

- 协调器状态为 `hk_active`，epoch 为当前版本。
- 香港持有可续期写租约，`/readyz` 返回 200。
- 新加坡同步数据并保持待命，Cloudflare 主池优先访问香港。

### 6.2 香港故障

1. Cloudflare 连续健康检查失败，将新请求切到新加坡。
2. 香港租约过期后，新加坡向协调器申请新 epoch。
3. 新加坡确认本地数据库可写且同步滞后不超过 5 分钟后取得租约。
4. 新加坡进入 `sg_active` 并开放业务写入。

若新加坡数据滞后超过 5 分钟，页面显示“备用数据过旧，禁止自动写入”，避免静默使用明显过期数据；管理员可查看最后同步时间后决定是否人工接管。

### 6.3 香港恢复与自动切回

香港进程启动后先处于 `hk_recovering`，其 `/readyz` 返回 503，因此 Cloudflare 不会提前切回：

1. 香港从新加坡拉取故障期间的全部事件。
2. 校验同步游标、关键表行数、最新事件 UUID 和抽样内容校验和。
3. 香港追平后向协调器申请切回。
4. 协调器停止新加坡写入、递增 epoch，并将租约交给香港。
5. 香港 `/readyz` 返回 200；Cloudflare 恢复主池流量。
6. 新加坡回到同步待命状态。

任一步校验失败都不自动切回，继续由新加坡提供服务并在设置页显示失败原因。

### 6.4 防止双站同时写入

- 每个写请求必须同时满足“本地角色为 active”和“协调器租约有效”。
- epoch 不一致的数据库写入拒绝提交。
- 节点失去协调器连接后仅在当前短租约有效期内继续处理；租约到期自动转只读。
- 健康检查只在应用、数据库、租约三者都正常时返回 200。

## 7. 备份与恢复

- 两站各自保留 PostgreSQL 数据卷。
- 活动站每天执行一次加密 `pg_dump`，通过 SSH/SFTP 复制到备用站。
- 每日备份保留 30 天，每次复制后校验 SHA-256。
- 每周在临时数据库自动执行一次恢复验证，确认备份可用。
- 增量同步用于 5 分钟内的数据连续性；数据库快照用于误操作、数据库损坏和全量重建，两者不能互相替代。

## 8. 页面与运维状态

设置页增加紧凑的“双站状态”区域，不新增独立大屏：

- 当前访问节点：香港或新加坡。
- 当前活动站和 epoch。
- 香港、新加坡应用及数据库健康状态。
- 对端最后同步时间、同步延迟和待同步事件数。
- 最近一次完整备份及恢复验证结果。
- 当前站 CRM 查询/移库通道登录数量。

所有页面顶部仅显示一个小型站点状态标记；异常时可点开查看原因。查询、移库和结单日志继续按当前页面分类，不把两个站点的运行中日志混在一起。

## 9. 部署与迁移顺序

1. 在现有代码中加入存储接口、PostgreSQL 后端、事件同步和迁移工具，保持文件后端测试通过。
2. 在隔离测试数据库中导入香港现有 `/app/data`，对条码数、匹配规则数、分销商数和账号数做前后校验。
3. 部署新加坡应用和数据库，执行首次全量快照，再验证增量同步。
4. 部署 Cloudflare 协调器、健康检查和主备负载均衡；先使用测试域名演练。
5. 演练香港应用停止、香港整机不可达、数据库不可写、网络分区和恢复切回。
6. 验证通过后，将 `crm.mlmll.cn` 切换到新架构。
7. 保留迁移前香港数据卷和数据库备份至少 30 天，确认稳定后再清理。

升级使用数据库迁移版本号，不在容器启动时覆盖现有数据。`docker compose up -d --build` 只更新镜像和执行向前兼容迁移，不重建数据库卷。

## 10. 验收标准

- 香港正常时，全部访问落到香港，新加坡不可写但持续同步。
- 停止香港应用后，`crm.mlmll.cn` 自动进入新加坡且可继续新增、修改和删除业务数据。
- 香港恢复时不会提前接流量；追平新加坡数据并校验后才自动切回。
- 正常网络下，两站新增、修改、删除的可见延迟不超过 5 分钟。
- 删除一条条码、分销商和产品匹配规则后，将旧节点离线再恢复，三类数据都不会复活。
- 同一同步事件重复发送不会产生重复记录。
- 模拟两站网络分区时，最多只有持有租约的一站接受写入。
- 查询报表 HTML 能从数据库完整打开，导出文件可重新生成。
- Windows、macOS 桌面版在没有 `DATABASE_URL` 时仍使用本地文件并通过现有核心流程测试。
- 每日备份能够在临时数据库成功恢复。
